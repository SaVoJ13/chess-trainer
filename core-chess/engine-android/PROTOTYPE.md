# Прототип рушія (Stockfish sf_19): звіт вимірювань

Дата: 2026-10-29. Автор: Шахове ядро. Гілка `feature/engine-prototype`. План: `docs/project_log.md`, запис Архітектора «сесія 7»; пороги: `docs/CONTRACTS.md` 3.4 (v0.7).

**Відхилення, які впливають на довіру до цифр:**

1. **Телефон був підключений до USB і заряджався** (`USB powered: true`, статус 2 або 4 «не заряджається» при ~90 %). Протокол вимагає «не на зарядці»; з USB-adb цього не зробити. Для суворого виконання потрібен wireless adb: питання до власника.
2. Телефон заблокований паролем. Щоб рушій не призупинявся, коли екран гасне (без цього 2 з 6 перших запусків зависали), debug-Activity ставить `FLAG_KEEP_SCREEN_ON | SHOW_WHEN_LOCKED | TURN_SCREEN_ON`. У тестах «у фоні» екран перейшов у `Dozing` (штатно, за таймаутом).
3. Пам'ять, збій і фон: повторів менше п'яти там, де вказано `n`. Решта по 5.
4. Дані `analyse` для remote зібрано з увімкненим трасуванням UCI в logcat (`log.tag.SfUci DEBUG`, ~350 рядків за 10 с), перший прогін без трасування зависав (розд. 8).
5. Файловий кеш ОС був теплий (мережа 98 МБ уже в page cache); на справді холодному пристрої читання мережі буде довшим.
6. Один пристрій, флагман: абсолютні цифри оптимістичні. API 26 і `armv8` без dotprod на ньому природно не перевіряються (є лише примусовий перемикач).

| Що | Байт | Примітка |

Рішення щодо мережі: **окремий asset** `assets/nnue/…` (одна копія для обох `.so`), копіюється у `filesDir/nnue/` при першому запуску. Вбудовувати в `.so` не стали: дві бібліотеки дали б по 98 МБ кожна (≈ 197 МБ). Ціна рішення: 98,5 МБ у `filesDir` на додачу до ~80 МБ у APK; перший запуск ≈ 0,95–1,2 с проти 0,42 с (копіювання ≈ 0,6–0,8 с, n = 3, `pm clear` між запусками). Файл мережі не комітиться (`.nnue-cache/`, завантажує Gradle-завдання `fetchNnue*` за URL з `official-stockfish/networks`, перевіряє SHA-256 за іменем). Альтернатива на майбутнє: одна спільна `libsfnet.so` з мережею (incbin) для обох бібліотек, без копії у `filesDir`; не пробували.

## 3. 16 КБ і API 26 (статична перевірка)

- `llvm-objdump -p <lib>.so | grep LOAD`: усі сегменти `LOAD` усіх трьох бібліотек `align 2**14`.
- `zipalign -v -c -P 16 4 app-debug.apk`: `Verification successful`, `.so` у APK `OK`.
- Лінкування зі `-Wl,--no-undefined` проти stub-ів API 26 (`ANDROID_PLATFORM=android-26`) пройшло: жодного символу bionic поза API 26. `sf_19` на Android обходить `shm_open`/NUMA/`sched_*` (`#if defined(__ANDROID__)`), вирівняне виділення йде через `posix_memalign`, не `aligned_alloc`.

| Критерій | in-process | remote (`:engine`) | Поріг | Статус |
|---|---|---|---|---|

**Потік `analyse`.** Поріг у 10 `Update`/с недосяжний для одного рядка PV за самою природою Stockfish: рушій друкує один `info … pv` на кожну глибину, а після глибини ~20 інтервал між рядками секунди (максимальна пауза 2–5 с в обох режимах). Кількість отриманих `Update` за 10 с збігається в обох режимах (22–26), тобто втрат у транспорті не видно, але прямого підрахунку «надіслано / отримано» не робили. Формулювання порога, ймовірно, треба змінити (наприклад, «жодної втрати подій» + частота на MultiPV 3–5). Рішення за Архітектором.

**Пам'ять.** Різниця зумовлена тим, що окремий процес несе власний ART і бібліотеки (~47 МБ у `:engine` понад Native Heap 235 МБ), тоді як PSS app у режимі remote нижчий лише на ~220 МБ (мережа і TT живуть в `:engine`). Мережа ≈ 109 МіБ у пам'яті (`NNUE evaluation … (109MiB …)`), `Hash 16`, `Threads 1`.

## 6. Сканування байткоду на API, відсутні в Android 8 (CONTRACTS 8, п. 11)

Метод: `dexdump -d` усіх `classes*.dex` фінального debug-APK (після D8 з `minSdk 26`, тож бекпорти й десугаринг уже застосовано), посилання з класів `com.github.bhlangonijr.*` (chesslib 1.3.7) і `org.apache.commons.lang3.*` (SW-007) звірені з `platforms/android-36/data/api-versions.xml` (`since` > 26). Скрипт: одноразовий, в репозиторій не додано. Перевірено 16 058 інструкцій виклику.

Результат: **одне** посилання на API новіше за 26: `java.lang.reflect.Type.getTypeName()` (API 28) у `commons-lang3` `reflect/TypeUtils`. З chesslib у `commons-lang3` викликається лише `StringUtils.isEmpty/isBlank/isNotEmpty/isNotBlank` (з `Board`, `Game`, `MoveList`, `GameLoader`), тому `TypeUtils` недосяжний із застосунку; ризик практично відсутній. Власний код `org.chesstrainer.*` (5 369 викликів): 0 звернень до API > 26. Окрема перевірка на емуляторі API 26 (п. 11) залишається за Android і UI.

Обмеження методу: перевіряються лише посилання на методи/поля/класи платформи; поведінкові відмінності версій не виявляються.

## 7. Знахідки під час прототипу

1. **`sf_19` не підтримує повторне створення рушія в процесі.** `OptionsMap::add` має `static usize insert_order`: другий `UCIEngine` у тому ж процесі не друкує опцій на `uci` (тому `capabilities` не прочитати). Код Stockfish не змінювали. Міст тримає один `UCIEngine` на процес: `stop()` гасить пошук і зводить `Hash`/`Threads` до 1, пам'ять мережі (≈ 109 МБ) **не повертається**. Тому в режимі remote процес `:engine` завершується разом із сервісом (`killProcess` в `onDestroy`): `stop()`+`start()` = новий процес, повернення всієї пам'яті. У режимі in-process повне звільнення пам'яті рушія неможливе без завершення процесу.
2. Збій у режимі remote виявляється через `DeathRecipient` (846 мс у тесті), Android сам планує перезапуск сервісу.
3. Android гасить/призупиняє застосунок із вимкненим екраном і блокуванням (інтермітентні зависання при вимкненому екрані): для вимірювань потрібен видимий екран.
4. Локаль пристрою українська: `String.format("%.1f")` дає кому. Зведення враховує.
5. Мережа 98 МБ у git не комітиться; CI має мати доступ до `github.com/official-stockfish/networks` і NDK `30.0.16248370` + CMake `4.1.2` (SDK Manager). Передати Android і UI (`.github/workflows/`).

## 8. Відкриті проблеми

- **Дві не діагностовані зупинки remote-аналізу.** Серія `analyse` у режимі remote двічі «застигла» (останнє повідомлення: старт нового процесу `:engine`, далі тиша > 15 хв) на 22–25-му рестарті. Третій прогін із повним трасуванням UCI і дампом потоків пройшов усі 30 запусків без зупинки, тож не відтворено й причину не встановлено. Підозри: гонка між `killProcess` старого сервісу і новим `bindService`; призупинення процесу ОС. Для дефекту «ізоляція збою» це не критерій, але для архітектури remote це ризик: потрібне окреме розслідування (лічильник перезапусків, таймаут на `RemoteTransport.close()`, watchdog).
- Ліцензія Ninja (SW-017) не прочитана.
- Затримка ходу Handicap не вимірювалась (`HandicapEngineService` ще не існує): накладні IPC наведено в розд. 5.
- Перевірка на справжньому Android 8 і на CPU без dotprod: немає пристрою.
